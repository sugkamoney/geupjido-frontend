# ADR-002: NAVER Maps 기반 Vite SPA로 데스크톱 웹을 먼저 개발한다

> 상태: **확정** · 날짜: 2026-09-19 · 영역: **프론트엔드**

## 맥락

급지도는 수도권 아파트 권역과 단지를 지도에서 탐색하는 서비스다. 백엔드는
Spring Boot REST API와 PostGIS를 사용하며 프론트엔드는 아직 초기화 전이다.
지도 제공자, 렌더링 방식과 초기 플랫폼 지원 범위를 결정해야 했다.

## 선택지

### MapLibre 기반 Vite SPA

공급자 종속성이 낮고 공간 레이어 제어가 자유롭지만 국내 베이스맵과 POI의
품질, 타일 공급자와 비용을 별도로 결정해야 한다.

### NAVER Maps 기반 Vite SPA

국내 지도와 지명·POI 품질을 활용하면서 정적 배포가 가능한 단순한 구조를
유지할 수 있다. 대신 NAVER Maps SDK, 약관과 호출 비용에 종속된다.

### NAVER Maps 기반 SSR 프레임워크

검색 노출과 서버 렌더링 확장에는 유리하지만 지도는 브라우저에서 실행되고,
초기부터 별도 프론트엔드 서버와 렌더링 경계를 운영해야 한다.

## 결정

- 지도 제공자는 NAVER Maps JavaScript API v3를 사용한다.
- React와 TypeScript 기반 Vite SPA로 시작한다.
- 검색 노출이나 서버 렌더링 필요가 확인되면 프레임워크 전환을 검토한다.
- 초기 제품과 품질 보증 범위는 데스크톱 웹으로 제한한다.
- 모바일 웹은 후속 제품 작업으로 연기한다.

## 이유와 trade-off

국내 지도 품질을 확보하면서 별도 Spring Boot 백엔드와 명확히 분리되는 단순한
FE 구조로 시작할 수 있다. 초기 사용 시나리오에 집중해 모바일 반응형 설계와
교차 기기 테스트 비용도 미룰 수 있다.

반면 지도 공급자 종속성과 호출 비용이 생기고, SPA는 검색 엔진에 노출할 공개
상세 페이지에 불리할 수 있다. 모바일 사용자는 초기 품질 보증 대상에서
제외된다. 이를 완화하기 위해 프로젝트 데이터 모델과 API는 GeoJSON 등 공급자
중립 형식을 유지하고 NAVER SDK 접근을 지도 어댑터에 격리한다.

## 재검토 조건

- 지역·권역·단지 상세 페이지의 검색 유입이 핵심 성장 경로가 된다.
- 페이지별 검색 메타데이터나 공유 미리보기가 필요하다.
- 모바일 사용자 비중과 모바일 전용 사용 시나리오가 확인된다.
- NAVER Maps 비용, 약관, 기능 또는 성능이 제품 요구와 맞지 않는다.

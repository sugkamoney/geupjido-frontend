# ADR-003: 지도 프론트엔드 상태와 API 계약을 URL·OpenAPI 중심으로 관리한다

> 상태: **확정** · 날짜: 2026-09-20 · 영역: **프론트엔드·API 연동**

## 맥락

지도 탐색은 확대·이동·검색·권역 및 단지 선택처럼 상태 변화가 빈번하다. 공유 링크,
새로고침과 브라우저 뒤로가기에 일관된 동작이 필요하며, 프론트와 아직 확정되지 않은
백엔드 지도 API도 같은 계약을 따라야 한다.

## 결정

- URL에는 선택한 권역 또는 단지의 공개 ID, 지도 중심 좌표, zoom, 활성 필터만
  저장한다. cluster ID와 일시적 UI 상태는 저장하지 않는다.
- 지도 이동·확대·축소처럼 연속적인 조작은 종료 시점에 현재 history 항목을 교체한다.
  검색 결과, 권역, 단지의 명시적 선택만 새 history 항목으로 추가한다.
- 지도 단지 표시는 임시로 zoom 0~11에서 미조회, 12~13에서 cluster, 14~21에서
  개별 단지로 전환한다. cluster 선택은 중심으로 zoom을 2단계 높인다.
- 단지 viewport 조회는 지도 조작이 끝난 뒤 250ms 동안 추가 조작이 없을 때 시작한다.
  이전 요청은 취소하며 현재 지도 상태와 맞지 않는 늦은 응답은 표시하지 않는다.
- 프론트 API 타입과 클라이언트는 백엔드가 생성한 OpenAPI JSON의 검토된 고정 사본을
  입력으로 생성한다. 백엔드 구현 전에는 같은 계약으로 MSW mock을 제공한다.

## 이유와 trade-off

공유할 가치가 있는 상태만 URL에 남기면 링크의 의미와 새로고침 복원성을 확보하면서도
연속 지도 이동으로 브라우저 history가 과도하게 늘어나는 일을 막을 수 있다. 안정적인
엔티티 ID를 사용하면 이름 변경이나 임시 cluster 재집계에도 링크가 유지된다.

OpenAPI 고정 사본과 생성 타입은 프론트의 수기 타입 중복을 줄이고, 계약 변경을 CI에서
확인할 수 있게 한다. 대신 백엔드 담당자가 OpenAPI 스키마와 버전 정보를 제공해야 하며,
실제 구현 전 mock과 최종 스키마의 차이를 검토해야 한다.

## 보류와 재검토

- 권역·단지 상세에서 우선 표시할 제품 정보
- 개별 단지 결과가 과도할 때의 지도 동작과 API 응답
- zoom 전환값과 cluster 집계 기준
- 실제 지도 viewport, 필터, 검색 API의 세부 OpenAPI 스키마

zoom 전환값과 cluster 규칙은 확정 디자인, 모바일 사용성, 실제 단지 분포와 API·렌더링
성능을 검증한 뒤 변경할 수 있다.

## 다음 논의 시작점

다음 세션에서는 백엔드 지도 OpenAPI의 고정 사본을 어떤 버전·전달 경로로 받을지부터
정한다. 이어서 검색 API와 지도 viewport API의 요청·응답 스키마, 오류 형식, MSW mock의
소유 범위를 확정한다.

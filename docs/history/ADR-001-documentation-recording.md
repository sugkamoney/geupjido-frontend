# ADR-001: 프로젝트 문서와 학습·결정 이력을 작업 중 함께 기록한다

> 상태: **확정** · 날짜: 2026-09-17 · 영역: **프로젝트 공통**

## 맥락

급지도 프론트엔드는 웹 개발을 우선하며 필요에 따라 모바일 웹도 지원한다.
프론트엔드 개발을 처음 진행하는 과정에서 제품 규칙, 기술 구조, 학습 내용과
결정 이유가 코드 변경과 함께 축적될 필요가 있다.

Git commit은 실제 변경 내용을 보존하지만, 개념을 이해한 과정이나 대안을
검토한 이유, 선택의 trade-off까지 충분히 설명하지는 못한다.

## 선택지

### Git과 커밋 메시지만 사용

변경 내용은 정확히 보존되지만 현재 제품 기준, 기술 설명과 학습 기록을
주제별로 탐색하기 어렵다.

### 하나의 문서에 모든 내용을 누적

시작은 단순하지만 제품 규칙, 현재 구조, 학습 내용과 과거 결정이 섞여 문서가
커질수록 현재 기준을 찾기 어려워진다.

### 목적별 문서 분류와 Git 이력을 함께 사용

현재 기준과 과거 판단을 분리하여 탐색할 수 있지만, 작업 중 관련 문서와
INDEX를 함께 갱신해야 한다.

## 결정

- 저장소 루트의 `AGENTS.md`에 작업 완료 전 문서 갱신을 검토하도록 지속적인
  지침을 둔다.
- 현재 제품 동작은 `docs/product/`, 현재 기술 구조는 `docs/architecture/`,
  프로젝트 맥락의 기술 학습은 `docs/learning/`, 중요한 판단의 이유는
  `docs/history/`에 기록한다.
- 비자명한 프론트엔드 질문과 답변은
  `docs/learning/frontend/q-and-a/`에 보존한다.
- 각 문서 분류의 `INDEX.md`를 탐색 시작점으로 유지한다.
- Git은 코드와 문서 diff의 원본 이력으로 사용하고, history 문서는 코드만으로
  알기 어려운 맥락과 판단을 기록한다.

## 이유와 trade-off

목적에 따라 문서를 분리하면 프론트엔드를 학습하는 중에도 현재 구현 기준과
학습 자료를 혼동하지 않고 찾아볼 수 있다. 반면 문서 관리 비용이 발생하므로
기계적이고 자명한 수정은 history 기록 대상에서 제외한다.

## 재검토 조건

- 문서 갱신이 반복적으로 누락되는 경우 자동 알림이나 검사 도구를 검토한다.
- 문서가 많아져 탐색이 어려워지는 경우 분류와 INDEX 구조를 세분화한다.
- 모바일 웹이 독립적인 제품 범위로 커지는 경우 제품 및 아키텍처 문서의
  모바일 웹 분류를 별도로 둔다.

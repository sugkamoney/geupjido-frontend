# 지도·검색·권역 상세 API 계약 조사와 설계 검토

> 상태: 첫 연동 범위 합의·읽기 계층 구현, 화면 연결 설계 논의 중 · 버전: 0.4 · 갱신: 2026-11-15

## 결론과 조사 경계

사용자는 지도·검색·권역 상세를 첫 연동 단위로 진행하고 좌표 누락·라벨 우선순위를
먼저 논의하는 데 동의했다(2026-11-15). 상태 카드·랭킹·투표함·월드컵 연동은 후속 범위다.
BE 조회 API는 제공되고 배포 서버에서도
응답하지만, FE fixture 모델과 구조·의미가 달라 source 교체만으로 연결할 수 없다.
아래 설계는 검토 제안이며 확정 제품 정책이나 구현 계획이 아니다.
최초 조사에서는 제품 코드를 변경하지 않았다. 이후 사용자의 ‘BE에 전달할 내용을 정리하고
지금 가능한 작업을 진행’ 요청에 따라 [BE 요청서](map-api-backend-request.md)와
[독립 읽기 계층](map-api-read-layer.md)을 작성·검증했다. 이후 사용자가 가능한 기존 화면 연결을 요청하고 BE 요청사항 전달 완료를 알렸다.
현재 연결 결과와 FE 임시 결정은 [기존 화면 연결 구조](map-api-ui-integration.md)를 따른다.
아래 조사 당시 대안과 미결 표를 현재 구현 상태로 오해하지 않는다.
새 의존성·상위 checkout·BE 변경, 게임 생성·투표, push·PR·merge는 수행하지 않았다.
조사와 선행 구현은 미커밋 상태로 검토했으며 이후 사용자 요청으로 의미별 로컬 커밋을 남긴다.

  `git ls-remote`로 원격 develop도 같은 SHA임을 확인했다.

## 현재 계약과 차이

경로 접두사는 `/api/v1/map`이다. 성공 응답은 envelope 없이 배열 또는 객체이며
`Cache-Control: no-store`다. 오류는 `{code, message}`이고 잘못된 입력은 400
`INVALID_REQUEST`, 없는 권역은 404 `ZONE_NOT_FOUND`다.

| API | 확인한 BE 계약 | FE 차이와 처리 제안 |
| --- | --- | --- |
| `GET /cities` | 전체 서비스 구·시, center, bounds, regionName, 두 급지 평균과 각 집계 대상 수 | overview는 유효 city bounds의 합집합으로 산출. 구·시를 모두 수용하고 `서울` 고정 경로 제거. 급지 없는 구·시도 유지 |
| `GET /zones?west=&south=&east=&north=` | polygon과 범위가 겹치는 권역. center, 두 급지·각 전체 순위/모수, rankingBasis, 단지 수·발행 유효표 수 | `MapLabel.area/bounds`, `Zone.polygon`을 채울 수 없음. 요약 모델과 geometry 분리. 중심이 화면 밖인 응답도 있을 수 있음 |
| `GET /complexes?west=&south=&east=&north=` | 범위 안 location이 있는 단지 핀. id, zoneId, cityName, zoneName, households. 투표 후보 여부와 무관 | 핀 모델에 직접 변환 가능. 가격·면적·준공연도는 이 응답에 없으므로 상세와 ID로 결합 |
| `GET /zones/{zoneId}` | `{zone, polygon, complexes}`. polygon은 GeoJSON 객체. complexes는 전체 목록이며 순위 null 허용 | 상세 단지는 zoneId·location이 없음. zoneId는 부모에서 상속 가능하나 위치는 별도 확보 필요. 기존 단일 좌표 배열 렌더러 확장 |
| `GET /search?q=` | `{cities,zones,complexes}`. 최대 3/5/6개. 단지 결과는 ComplexPin | 전체 Zone을 요구하는 SearchTarget 대신 ID와 이동 좌표 중심 참조로 변경. 선택한 zoneId로 상세 조회 |
| `GET /status` | 마지막 집계 스냅샷, 전환/수집 수, 발행·다음 예약 시각(null 가능) | SDK 로딩 상태와 다른 제품 통계다. 이번에는 계약만 확인하고 새 카드 구현은 후속 권장 |

근거는 BE `MapController`, `MapView`, `MapQueryService`, `MapQueryRepository`,
`MapExceptionHandler`, `MapApiIT`와 `docs/architecture/map-tab-api.md`다.
지도 범위는 유한한 WGS84 경도·위도이며 `west < east`, `south < north`가 필수다.
현 API에는 cluster·zoom 매개변수·페이지 분할·ETag 계약이 없다.

### 급지·순위·금액 의미

- initialTier와 voteTier, rankingBasis 및 각 rank/total을 원형대로 보존한다.
  null은 0이나 다른 기준의 값으로 대체하지 않는다. 구·시 평균의 각 대상 수도 보존한다.
- initialTier는 원본 외 추정 편집값을 포함한다. `초기 급지`로 안내하며
  `배치표 1.1 원본`·출처 날짜를 임의로 넣지 않는다.
- 첫 화면은 초기 급지를 기본으로 제안한다. 민심 전환 UI 포함 여부는 미결이다.
  권역마다 voteTier 유무로 자동 선택하면 서로 다른 기준을 한 지도에서 혼합하므로 권장하지 않는다.
  민심 화면의 null은 `모으는 중`, 초기값 null은 정보 없음으로 구별하는 안이다.
- 상세 단지 순위는 rankingBasis가 INITIAL이면 ㎡당 대표 가격, VOTE이면 투표 점수다.
  지도 표시 기준과 단지 순위 기준은 독립적이므로 각각 명시해야 한다.
  서버 순서와 zoneRank를 사용하고 `index + 1`로 순위나 상위 3개 강조를 생성하지 않는다.
  비활성 투표 후보도 목록에 남으며 VOTE에서 순위·점수는 null일 수 있다.
- price는 만원, representativeArea는 실제 전용면적 ㎡, lastDealDate는 대표 거래 계약일이다.
  `대표 거래가`로 안내하고 총액순/최근 거래순으로 설명하지 않는다.
  approvalDate는 날짜로 보존하고 표시 때 연도를 추출한다. null 가격·면적·날짜는
  0원/0㎡로 바꾸지 않고 해당 정보 없음으로 표시한다.
- 유효표 수는 마지막 발행 기준이다. 이번 조회에서 투표 전환을 FE가 계산하거나 약속하지 않는다.

금액 단위 근거: BE `docs/history/2026-10-28-complex-representative-price.md`,
`docs/architecture/worldcup-card-api-contract.md`. 현재 FE `formatPrice`의 만원→억원
계산은 재사용할 수 있지만 API null을 받는 경계 처리가 필요하다.

### 검색의 추가 차이

FE SDD는 일치 위치·이름 길이 동률을 ID 순으로 정하지만 BE는 이름 비교도 사용한다.
단지는 공백을 뺀 이름 길이를 사용한다. 서버가 제한한 상위 결과만 재정렬해도
기존 전체 후보의 ID 동률 정책을 보장할 수 없다. 서버 순서를 수용하고 SDD를 갱신하는 안을 권장한다.
엄격히 기존 정책을 유지하려면 BE 협의가 필요하며 이번 작업에서 BE를 수정하지 않는다.

BE 검색어는 1~80자이고 현재 FE는 최대 길이 검증이 없다. 빈 값/공백은 기존처럼
요청하지 않고, 긴 입력에는 안내하는 정책을 논의해야 한다. 조합 중 검색·IME Enter 방지·
화살표·Escape·원문 강조·화면 밖 검색은 유지한다. FE 입력 revision과 abort 무시 공급자에
대한 오래된 응답 차단도 유지한다. 요청 빈도 제한은 debounce를 추가하되 조합 중 조회를 막지 않는 안이다.

## FE에서 해결할 구조와 남는 제약

### 요약·상세·선택 상태 분리

API DTO → 검증/변환 → UI 모델 경계를 둔다. ZoneSummary, ZoneGeometry,
ComplexSummary/위치 참조를 분리하고 표시용 단일 grade/value를 원본 데이터로 사용하지 않는다.
선택은 zoneId/complexId로 유지하며 viewport 목록에서 사라져도 지우지 않는다.
검색 선택은 id·zoneId·location만으로 이동한 뒤 상세를 독립적으로 로드한다.
핀 선택은 카메라 유지, 목록/검색 선택은 현재 UX의 이동·모바일 접힘을 유지한다.

실제 데이터 화면과 fixture 검토 경로를 명시적으로 구분한다. 실제 화면에서 API 실패를
fixture로 자동 대체하지 않는다. 특히 현재 fixture 월드컵과 타임라인이 실제 권역 ID를
처리한다고 간주할 수 없다. 실제 화면에서는 미연동 진입을 비활성/안내하고 검토 경로에
fixture 기능을 남기는 안을 권장하며 제품 결정이 필요하다.

### viewport 비동기 파이프라인

기존 TanStack Query provider를 활용하고 새로운 전역 상태 라이브러리는 추가하지 않는 안이다.
SDK ready와 양수 viewport 크기 이후 adapter projection의 화면 네 모서리로 범위를 계산한다.
레이아웃 frame은 카메라 중심 계산에 사용하고 조회는 전체 지도 컨테이너 범위를 기준으로 제안한다.
위경도 유효성·크기 0·국제 날짜변경선 같은 API 미지원 범위를 검증한다.

- camera 구독의 revision은 animation 중에도 바뀐다. overlay projection 갱신과 HTTP 요청을
  분리하고 후자는 짧은 debounce 뒤 조회한다. 초기 후보는 200ms이며 실측 후 조정한다.
- zones는 권역 표시 단계(12.5 이상), complexes는 핀 표시 단계(14.5 이상)에서 요청한다.
  선택 상세/검색 핀은 낮은 줌에서도 별도로 유지한다. cities는 초기 로드와 재검증에 사용한다.
- query key에 리소스·bounds를 포함하고 signal 취소와 최신 요청 식별을 함께 사용한다.
  선택 상세 응답은 해당 ID에만 반영하고 오래된 viewport 응답이 새 화면을 덮지 않게 한다.
- 로딩·빈 결과·실패·재시도를 지도 SDK 오류와 별도로 표시한다. 범위가 달라진 이전 결과를
  현재 범위의 완전한 결과로 표시하지 않는다. 빈 배열은 이전 범위 결과를 비운다.
- HTTP no-store와 클라이언트 메모리 캐시는 다르다. 초기안은 staleTime 0,
  자동 polling 없음, 재진입/포커스 복귀 재검증이다. 이전 값 유지 여부는 갱신 안내와 함께 설계한다.
  400/404는 자동 재시도하지 않고 네트워크·5xx는 제한 재시도한다. 최종 옵션은 구현 계획에서 고정한다.

### 경계·라벨 충돌

BE DB는 MultiPolygon(4326)이고 상세는 `ST_AsGeoJSON(polygon, 6)`를 사용한다.
FE는 GeoJSON `[longitude, latitude]`를 LatLng로 바꾸고 모든 polygon/ring을 보존해야 한다.
선택 면은 SVG path의 evenodd 채움 등으로 hole을 비워 렌더하는 안이다.
첫 외곽선만 사용하거나 섬을 선으로 연결하면 안 된다. 전체 유효 외곽 좌표에서 상세 bounds를
도출할 수 있지만 권역 목록 단계의 면적/경계를 그럴듯한 사각형으로 생성하지 않는다.

라벨 충돌의 기존 “넓은 권역 우선”은 목록에 면적이 없어 그대로 구현 불가다.
FE 단독 안은 선택 우선 + 안정적인 ID 순으로 정책을 바꾸는 것이다.
현재 정책을 반드시 유지하려면 목록 면적 제공 등 BE 계약 협의가 필요하다.
구·시 bbox 면적을 권역 실제 면적으로 대체하거나 모든 권역 상세를 미리 조회하는 안은 권장하지 않는다.

SRID 지정은 좌표 변환이 아니다. 수집 코드의 `ST_SetSRID`와 타입 선언만으로 실제 좌표
정확성·한강 제외를 입증할 수 없다. 실제 SDK에서 경계·중심·단지 위치를 대조해야 한다.

### 좌표 없는 상세 단지

기존 핀/검색에서 위치를 아는 ID는 결합할 수 있다. 모르는 단지의 위치를 이름 검색으로
찾는 것은 동명·결과 최대 6개 때문에 ID 조회를 보장하지 못한다.

| 대안 | 가능한 범위·제약 | 권장 |
| --- | --- | --- |
| 상세 geometry의 bbox로 `/complexes` 추가 조회 후 zoneId·id 결합 | FE만으로 개선 가능. 주변 권역도 응답하고 경계 밖으로 매칭된 점·location null을 모두 해결한다고 보장할 수 없음 | 제한을 명시한 임시안 |
| 상세 단지에 location 추가 또는 단지 ID 조회 API 제공 | 화면 밖 단지를 정확히 찾는 계약. 원래 위치가 없는 단지의 nullable 정책도 필요 | 완전한 목록 이동을 위한 BE 협의안 |
| 위치 없는 행도 선택하되 위치 이동 불가 안내 | 전체 목록은 유지 가능. 기존 “목록 선택은 해당 단지로 이동” 수용 기준의 예외가 생김 | 제품 승인 필요 |

권역 중심을 단지 위치로 넣지 않는다. 아래 표본 측정은 임시안의 가능성을 뒷받침하지만
FE만으로 기존 목록 이동 수용 기준을 모두 충족한다고 약속할 근거는 아니다.

| `gangnam-apgujeong` | 9 | 14 | 9 | 0 | 1 / 0 |

세 표본의 상세 단지 141개는 모두 좌표를 확보했으나, 주변 권역 핀도 함께 반환됐다.
전체 282개 권역의 보장이나 응답 지연·브라우저 성능 측정은 아니다. GeoJSON 소수 6자리
반올림으로 생기는 bbox 경계 오차도 후속 검증 대상이다. BE DB의 location은 nullable이므로
표본 성공만으로 앞으로도 누락이 없다고 가정할 수 없다.

검단 표본에서 실제 다중 면과 많은 hole을 확인했다. 첫 ring만 그리는 방식은 실제 데이터에서
정보를 잃는다. hole 보존은 가상의 예외 처리가 아니라 이번 연동의 필수 geometry 범위다.

권장 협의안은 상세 `Complex`에 nullable location을 추가하는 것이다. zoneId는 상세 부모에서
얻을 수 있으므로 중복 제공이 필수는 아니다. FE가 필요한 위치를 상세 요청 한 번에 확보하고,
위치가 원래 없는 단지는 그대로 구분할 수 있다. 별도 단지 ID API는 다른 사용처가 생길 때
대안으로 검토한다. 이번 조사에서는 BE 변경이나 협의 메시지 발송을 하지 않는다.

BE 개선을 기다리지 않는다면 bbox 추가 조회를 임시로 사용하고, 좌표 미확보 시 행 선택과
상세 정보를 유지하되 이동을 생략하고 위치 정보 없음/조회 실패를 구분해 안내하는 제품
예외가 필요하다. 모바일에서는 위치를 확보한 뒤 카메라 이동·시트 접힘을 적용하는 안이다.
이는 아직 승인되지 않았으며 관련 수용 기준을 변경하기 전에 사용자와 결정한다.

## OpenAPI·환경

배포된 생성 OpenAPI를 임시 폴더에 내려받아 6개 지도 경로와 DTO를 대조했다.
원본 SHA-256은 `eea232dd1549a8422b90e4823b1c047a5d8cd80f284ff7f9941dd63d4241c527`다.
임시 경로는 `/private/tmp/geupjido-map-review-openapi-20261115.json`이며 영구 계약 사본이 아니다.
배포 응답의 빌드 SHA는 검증하지 않았으므로 BE develop과 동일한 빌드라고 단정하지 않는다.

스키마에는 nullable·required 표현이 부족하고 polygon은 JsonNode이며 지도 400/404도 명세되지 않았다.
실제 voteTier null과 BE 테스트의 가격·순위 null이 타입 정보보다 우선하는 증거다.
고정 스키마 + 생성 타입 + 명시적 nullable/geometry 런타임 검증 경계를 권장한다.
보완한 타입은 BE 생성 원본과 구분하고 스키마 보강은 BE 협의 사항으로 남긴다.
package.json에는 openapi-typescript/openapi-fetch가 아직 없어 기반 문서의 도입 예정과
실제 설치 상태를 구별한다. 이번에는 스키마를 레포에 고정하거나 의존성을 설치하지 않았다.

브라우저는 상대 경로 `/api`를 사용한다. 현재 Vite proxy는 로컬 BE 고정이므로
구현 때 서버 측 개발 환경 변수로 대상을 선택하도록 제안한다. 환경 주소는 이 문서에 복사하지 않는다.
production의 동일 출처 프록시는 Vite dev proxy와 별도로 확인한다.
지도 공개 GET은 게임 쿠키 없이 조회됐으며 월드컵의 Secure 쿠키·Safari HTTPS 검증은 후속 범위다.

## 조사 요청 재개 시 재점검

이번 재개에서는 FE HEAD `2fe3b43`과 BE 사본 `a3e7a28`을 확인하고,
controller·읽기 모델·조회 SQL·검색 서비스·MapApiIT 및 현재 FE 선택/렌더 구조를 다시 대조했다.
BE 사본의 git 작업 트리는 깨끗하다. 재개 시 이미 존재하던 읽기 계층·계획·SDD 변경은
보존했으며 이번 재점검에서 제품 코드·의존성은 추가 수정하지 않았다.

단지 좌표와 권역 면적은 여전히 현재 BE DTO에 없다. 따라서 기존 UX를 모두 유지하는
연동과 FE만으로 가능한 제한적 연동을 구별해야 한다. 우선 권장안은 상세 단지의 nullable
location과 권역 면적 제공을 협의하는 것이다. BE 보완을 기다리지 않는 안은 bbox 조회로
좌표를 결합하되 위치 미확보 행의 이동 예외와 라벨 우선순위 변경을 제품 결정으로 남긴다.
[BE 요청서](map-api-backend-request.md)는 전달 가능한 초안이며 발송하지 않았다.

생성 OpenAPI의 새 네트워크 조회는 성공하지 못했고 권한 확장 재시도도 중단됐다.
임시 폴더의 기존 스키마를 읽어 지도 6개 경로와 required/geometry 명세 공백을 대조했다.
위 배포 GET·표본·211개 테스트 결과는 기존 기록이며 이번 재개에서 재실행한 결과가 아니다.
실제 API 최신 배포·SDK·모바일 브라우저 결합의 성공을 새로 주장하지 않는다.

디자인 작업공간 `82:5`의 metadata에서 지도 줌 단계, 기준 전환, 상태 카드와 투표 버튼을
확인했다. 이는 화면 구성 확인이며 새 시안의 시각 검증이나 구현 승인으로 취급하지 않는다.
현재 논의의 다음 결정은 좌표·면적 BE 보완을 전제로 기존 UX를 유지할지,
FE 임시 대안의 제한을 먼저 수용할지다. 미결 결정은 이 문서만으로 확정하지 않는다.

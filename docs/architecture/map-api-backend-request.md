# 지도 API 연동을 위한 BE 계약 보완 요청

> 상태: 사용자 전달 완료·BE 보완 계약 대기 · 버전: 0.2 · 갱신: 2026-11-15

## 2026-11-20 현재 상태

면적·상세 location·nullable 필수 명세 요청은 BE PR #188 배포와 실제 응답으로 확인하고 FE에 반영했다. 아래는 당시 전달 요청이며 한강 경계 보완은 별도 미발송 초안으로 남긴다.
현재 구조와 검증은 [마무리 검증](map-integration-finalization.md)을 따른다.

## 배경

FE 첫 연동 범위는 지도·검색·권역 상세이며 데스크톱과 모바일 웹을 함께 지원합니다.
BE develop `a3e7a28`의 지도 조회 계약과 배포 GET 응답을 확인했습니다.
기존 탐색 UX를 유지하기 위해 아래 두 필드를 우선 요청합니다.
이 문서는 FE에서 작성한 요청안이며 BE와 합의되거나 구현된 계약이 아닙니다.
사용자는 2026-11-15 요청사항을 전달했다고 알렸습니다. 이 세션에서 별도 발송하지 않았습니다.

## 우선 요청 1: 권역 상세 단지의 좌표

**대상:** `GET /api/v1/map/zones/{zoneId}`의 `complexes[]`

목록에서 단지를 선택하면 해당 단지로 지도를 이동하고 핀을 선택하는 동작이 필요합니다.
현재 상세 단지에는 위치가 없어 화면 밖 단지를 선택했을 때 이동 목적지를 알 수 없습니다.

기존 단지 필드를 유지하면서 아래 필드를 추가하는 안을 요청합니다.

```json
{
  "location": { "longitude": 127.0, "latitude": 37.5 }
}
```

- 핀·검색 응답의 location과 같은 의미·좌표계(WGS84 경도/위도)를 사용합니다.
- DB 위치가 없으면 `location: null`로 보내고 권역 중심 등으로 대체하지 않습니다.
- 단지 ID에 대해 상세·지도 핀·검색의 위치가 일치해야 합니다.
- 비활성 후보·가격 없는 단지도 전체 상세 목록에 유지합니다.
- zoneId는 상세 부모에서 확인할 수 있으므로 추가가 필수는 아닙니다.

**완료 확인:** viewport 밖 단지를 상세에서 선택해 정확한 위치로 이동할 수 있고,
위치 없는 단지는 null로 구분되며 기존 필드·목록 순서·rank null 정책이 유지됩니다.

FE 임시 대안은 권역 경계의 bbox로 단지 핀을 추가 조회하는 방법입니다.
3개 권역 141개 단지는 모두 결합됐으나 전체 데이터·향후 데이터까지 보장하지 않습니다.
별도 단지 ID 조회 API보다 상세 필드 추가를 우선 제안합니다.

## 우선 요청 2: 권역 목록의 면적

**대상:** `GET /api/v1/map/zones`, 검색의 `zones[]`, 상세의 `zone`

권역 라벨이 겹치면 현재 정책은 ‘선택 권역 우선 → 넓은 권역 우선’입니다.
목록에는 중심만 있어 FE에서 권역 면적을 알 수 없습니다. 모든 상세 경계를 미리 받으면
목록과 상세를 분리한 API의 이점을 잃습니다.

공통 Zone 응답에 `areaSquareMeters: number`를 추가하는 안을 요청합니다.
이 이름은 제안이며 BE 명명 규칙에 맞춰 조정할 수 있습니다.

- 단위는 ㎡, 유한한 양수이며 동일 권역은 목록·검색·상세에서 동일한 값을 사용합니다.
- WGS84 좌표 숫자에 단순 평면 면적을 적용한 제곱도 값은 사용하지 않습니다.
  지리 면적 계산 또는 적절한 투영을 사용해 단위를 확인해 주세요.
- 여러 polygon을 포함하고 hole은 제외한 권역 실제 경계의 면적을 사용합니다.
- bbox 면적·단지 수를 면적 대신 보내지 않습니다.

**완료 확인:** 같은 viewport의 겹치는 라벨에서 선택 권역이 먼저 표시되고,
나머지는 제공 면적 내림차순으로 재현 가능하게 배치할 수 있습니다.
동일 면적의 최종 ID 순서는 FE에서 정합니다.

## 함께 확인할 명세 사항

1. OpenAPI에 initialTier/voteTier, 각 rank, 상세 price/area/date/score/location의
   실제 nullable 여부와 필수 필드를 표시해 주세요.
2. polygon을 일반 JsonNode보다 구체적인 Polygon/MultiPolygon 계약으로 표현할 수 있는지
   확인해 주세요. FE는 여러 면과 hole을 보존합니다.
3. 지도 400 `INVALID_REQUEST`, 상세 404 `ZONE_NOT_FOUND`의 `{code,message}` 계약과
   검색어 1~80자 제한을 명세에 포함해 주세요.
4. 검색 동률은 FE 기존 ID 순서와 BE의 이름 비교 순서가 다릅니다.
   BE 현재 정렬을 유지하는 것이 의도인지 확인 부탁드립니다.
5. 호환되는 필드 추가로 제공 가능한지, 배포된 생성 OpenAPI와 확인할 수 있는
   계약 버전/commit을 함께 알려 주세요. FE는 고정 스키마에서 타입 생성할 예정입니다.

## FE 진행 범위

BE 보완 전에도 기존 5종 조회 API의 HTTP·응답 검증·null·GeoJSON 경계 처리를 진행합니다.
단지 위치 누락 예외, 라벨 우선순위 변경, 급지 기준 전환, 검색 정렬 정책을 임의로 확정하지 않습니다.
현재 조사에서 BE 코드 변경·게임 생성·투표 요청은 하지 않았습니다.

근거와 표본 측정: [FE 계약 조사](map-api-integration-review.md).
환경 주소·키·배포 민감 정보는 이 요청서에 포함하지 않습니다.

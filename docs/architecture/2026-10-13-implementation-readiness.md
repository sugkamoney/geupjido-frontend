# 백엔드·디자인 핸드오프 구현 준비 점검

> 확인 날짜: 2026-10-13 · 후속 확인: 2026-10-27, 2026-11-10 · 상태: 월드컵 API 연동 착수 가능, 지도·검색·상세 API 대기

## 2026-11-10 백엔드·디자인 후속 확인

### 백엔드

GitHub에서 backend `develop`의 `7e5b8a109f86e86d2fe7017761be6fc6c9d3e6de`
(PR #150 병합)를 shallow clone해 문서·controller·migration을 읽기 전용 확인했다.
10-27 확인 이후 PR #94~#150이 반영됐다. 서버·DB·테스트는 실행하지 않았다.

- 데이터: 마장동 권역 추가, 서울 149개·경기 130개(총 279개) 권역 확정과 단지
  재배정, 단지 대표 시세·권역 내 초기 순위, 실거래 주간 자동 갱신, 권역 인접
  데이터, 투표 후보 활성 기준(권역·좌표·사용승인일·300세대 이상·대표 매매 거래).
  백엔드 기록의 로컬 기준 활성 권역 274개·활성 단지 3,522개(11-02)다.
- 제품 controller가 처음 생겼다. 모두 `/api/v1/worldcup` 아래다.

| 기능 | 엔드포인트 |
|---|---|
| 권역 목록·시작 가능 여부 | `GET /zones` (`zoneId`, `cityName`, `zoneName`, `tier`, `activeComplexCount`, `canStart`) |
| 인접 대체 권역 | `GET /zones/{zoneId}/alternatives` |
| 게임 시작 | `POST /games`(배너, 서울 60%·경기·인천 40% 추첨), `POST /zones/{zoneId}/games`(권역 진입) |
| 이어하기 | `GET /games/current` (없으면 `404 GAME_NOT_FOUND`) |
| 판 확정 | `PUT /games/current/rounds/{n}/vote` (`{"selectedComplexId"}`), `PUT .../rounds/{n}/skip` |
| 권역 급지·권역 내 단지 순위 | `GET /zones/{zoneId}/ranking` (`rankingBasis` `INITIAL`/`VOTE`, `lastCompletedAt`) |

정책은 다음과 같다. 상세는 백엔드 `docs/architecture/worldcup-game-api.md`,
`worldcup-card-api-contract.md`, `worldcup-zone-selection-api.md`,
`worldcup-match-generation.md`를 따른다.

- 익명 방문자: 서버가 `gjd_uid` 쿠키(HttpOnly·SameSite=Lax·365일)를 발급한다.
  교차 출처 FE는 `credentials: "include"`가 필요하고 `localhost`와 `127.0.0.1`을
  섞지 않는다. local 허용 출처는 `localhost:5173`·`5175`이며 dev·prod는 미설정이다.
- 게임: 시작 응답에 10판(`matchups`)을 한 번에 담는다. 같은 권역 대결은 최대 4판,
  나머지는 급지 ±0.2(부족하면 ±0.3) 다른 권역 대결이다. 미완료 게임이 있으면
  새 시작 요청도 기존 게임을 `200`으로 돌려준다. 판은 1번부터 순서대로 확정하고
  선택·건너뛰기는 바꿀 수 없다.
- 하루 한도: 한국 날짜 기준 익명 방문자당 새 게임 6개(60판). 초과는
  `429 DAILY_GAME_LIMIT_REACHED`다.
- 선택 비율: 판 확정 응답의 `roundResult`가 좌우 정수 퍼센트(합 100)를 준다.
  서로 다른 방문자 10명 미만이면 `available:false`다.
- 급지 반영: 한국 시간 0시부터 3시간마다 누적 유효표를 다시 계산한다. 권역별
  유효표 50표·방문자 10명·권역 간 유효표 20표를 모두 채운 권역만 `VOTE`로
  전환한다. 급지는 소수 첫째 자리이고 1.0~5.9로 제한한다.
- 카드 필드: `complexId`, `name`, `cityName`, `zoneName`, `zoneTier`,
  `households`, `approvalYear`, `representativeSale`(면적㎡·가격 만원·계약일).
  가까운 역·한 줄 설명·사진·점수·순위는 제외됐다.
- 오류: `{code, message}` 형식이다. `409 GAME_UNAVAILABLE`, `400 INVALID_VOTE`·
  `INVALID_ROUND`, `409 VOTE_OUT_OF_ORDER`·`VOTE_ALREADY_RECORDED`·
  `ROUND_ALREADY_SKIPPED`가 있다.
- 실제 브라우저의 쿠키 유지와 허용·차단 출처는 백엔드 PR #149에서 로컬 Chrome으로
  검증했다고 기록돼 있다. 배포 도메인의 쿠키·CORS는 미검증이다.

미결 이슈 #151은 공유 개발 서버(EC2·RDS·Redis)와 FE 연동 검증을 다룬다.
지도·검색·상세 API와 geometry, 전체 권역 랭킹, 리포트, 서비스 통계(참여 인원·표
수·다음 반영), 다른 사람의 월드컵 타임라인 API는 아직 없다.

### 현재 FE 월드컵 source와의 차이

| 항목 | 현재 FE `WorldcupSource` | 백엔드 API |
|---|---|---|
| 대진 단위 | `loadMatch(zone, cursor)`로 한 판씩 요청 | 게임 시작 시 10판, `nextRoundNumber`로 진행 |
| 대진 종류 | `kind: 'zone' \| 'apartment'` | `type: CROSS_ZONE \| WITHIN_ZONE` |
| 카드 설명 | `description` 한 줄 설명 | 제외 |
| 선택 결과 | fixture의 비율 공개·숨김 시나리오 | `roundResult.available`·`leftPercent`·`rightPercent` |
| 식별·한도 | 없음 | `gjd_uid` 쿠키, 하루 6게임, 이어하기 |
| 타임라인 | 검토용 다른 사람 예시 | API 없음 |

실제 연결 전 source 계약을 백엔드 응답에 맞춰 다시 정하고, 쿠키 전송을 위한
개발 프록시 또는 허용 출처 구성을 정해야 한다.

사용자가 제공한 `민심급지도 브랜드 시트_11.10v.html`을 headless Chrome으로
렌더링하고 소스 텍스트를 확인했다. 이전 버전 파일이 없어 직접 비교하지 못했다.

도움말, 10판 결과·30판 내 선택 리포트·하루 60판, 줌 12.5(권역)·14.5(단지) 확정,
심볼(집 안에 접은 지도)과 앱 아이콘 규칙을 담고 있다. 색 토큰은 "Figma 10/8 기준과

- Figma의 "표 모으는 중 79/80표"와 백엔드 전환 조건(50표·10명·권역 간 20표)이 다르다.
- 디자인의 162개 권역은 데모 값이며 백엔드는 279개다.
- 브랜드 시트의 대진 비율 옵션 "3:7 (권역이 다 찬 뒤)"는 백엔드에 없다.
- 랭킹·리포트·상태 팝오버·타임라인은 화면만 있고 API가 없다.

이 확인은 정책 확정이 아니며 위 불일치는 기획·백엔드와 합의해야 한다.

## 2026-10-27 백엔드 후속 확인

GitHub에서 backend `develop`의 `036590392a04ae54ee6015b4759f02d1e2866031`
(PR #92 병합), 전체 파일 트리, PR 검증 기록과 미결 이슈 #91을 읽기 전용 확인했다.
단지 수집·재개/월간 처리, 실거래 저장·수동 적재에 이어 NAVER Geocoding과 PostGIS
권역 배정까지 구현됐다. PR #92의 Build and Test는 성공했다.

백엔드 기록의 로컬 DB 4,307개 단지 중 좌표는 4,306개, 권역 배정은 4,293개다.
배정 점이 해당 권역 밖인 건은 0개이며 법정동 코드 충돌 7개는 승인된 단지별
예외다. 이는 백엔드 로컬 검증 기록이며 운영 DB 준비나 이번 세션의 재검증을 뜻하지 않는다.
이슈 #91은 마장동 권역 추가와 위치 후보 12건, 단지별 예외·테스트 데이터 정리를
다룬다. 전체 파일 트리에 제품용 controller는 아직 없으며 match/vote/tier/user는
package-info 수준이다. 실제 지도·검색·상세 및 월드컵 API 연결은 계속 대기한다.

실제 SDK 통합과 별개로 공개 API·OpenAPI, 지도 응답 필드, 가격·급지·집계 정책을
합의해야 한다. 데이터 적재와 좌표 배정 완료를 제품 API 제공으로 간주하지 않는다.
이번 확인에서는 서버·DB·테스트를 실행하지 않았다.

## 확인 범위와 한계

백엔드 원격 기본 브랜치 `develop`을 임시 폴더에 shallow clone하여 코드를
검토했다. 기준은 [`dfb7cc4282979232f616113dd25704ee0b38b405`](https://github.com/sugkamoney/geupjido-backend/tree/dfb7cc4282979232f616113dd25704ee0b38b405)
(2026-10-05, 실거래 수집 서비스 PR #71 병합)다. 원격 브랜치 이름도 조회했지만
모든 feature 브랜치의 코드를 검토한 것은 아니다. 서버를 실행하거나 실제 DB,
배포된 API, 백엔드 테스트를 검증하지 않았다. 백엔드 파일은 수정하지 않았다.

디자인 MD 00~09, 별도 기획 논의 문서, HTML 3개를 읽었다. Figma의 Foundations,
Components, Screens 구조와 메인 화면 변수, 메인·월드컵 선택 직후 스크린샷을
확인했다. 모든 화면·variant의 정밀 검증은 구현 시 진행한다. HTML은 브라우저
도구 연결 오류로 소스만 검토했으며 실제 클릭 동작을 테스트하지 않았다.

## 백엔드 구현 현황

| 영역 | 코드에서 확인한 구현 | FE 연동에 남은 일 |
|---|---|---|
| 지역·권역 | Region/City/Zone, repository, GeoJSON 경계 import, 공간 schema | 공개 지도 DTO·조회 API, 구 평균 급지·라벨 정보 |
| 단지 | Complex, repository, 목록·기본정보 수집, 단건·일괄 저장 runner | 좌표·권역 매핑과 활성화, viewport·상세·권역 내 순위 API |
| 실거래 | ApartmentTrade 모델·schema·repository, 외부 API client·mapper·collection service | 단지/권역 매핑, 저장·집계 흐름, 대표 가격·면적 갱신과 조회 계약 |
| 지도·검색 | 공개 controller 없음 | 경계·라벨·핀·검색 계약 정의 |
| 월드컵·투표·급지·사용자 | match/vote/tier/user는 package-info 수준 | 대진, 투표·넘김, 익명 식별/인증, 비율·타임라인·급지 산정 구현 |
| OpenAPI | Springdoc 의존성과 OpenApiConfig 존재 | 제품 endpoint 명세와 고정 JSON 산출물 |

`Complex` 생성 시 `zone`, `location`, `price`, `representativeArea`는 설정되지
않고 `active=false`로 시작한다. 필드가 존재한다는 사실만으로 화면에 쓸 실제
데이터가 준비되었다고 판단할 수 없다. 최신 실거래 collection service는 외부
응답을 모델 목록으로 변환해 반환하며, 해당 서비스 자체가 저장·가격 갱신을
수행하지 않는다.

## 기존 설계와 새 핸드오프의 차이

| 항목 | 9월 설계 | 새 디자인 동작 기준 |
|---|---|---|
| 지도 표시 | 시·권역 경계 Data Layer, 최신 원격 문서 기준 zoom 12~13 cluster / 14~21 complex | 구·권역 라벨, 선택한 권역만 면 표시, cluster UI 없음 |
| 줌 | 정수화해 API 요청 | 구/권역 12.5, 단지 핀 14.5, 최소 9.5·최대 17 |
| 권역 상세 | 구체 화면 미정 | 급지·단계·권역 내 단지 시세순 목록·비교 진입 |
| 제품 범위 | 지도 탐색 중심 | 검색·월드컵 모달·타임라인·내 선택 누적 판 포함 |
| 작은 화면 | 최소 QA 1280×720 | 시각 기준 1920×1080, 더 좁은 화면의 축소 정책 미정 |

기존 [지도 API 설계](../superpowers/specs/2026-09-19-map-api-and-runtime-design.md)의
cluster·zoom 규칙을 새 UI에 그대로 적용하지 않는다. SDK 실수 zoom과 서버 조회
zoom의 관계, viewport 상한·응답 제한 시 UX를 새 계약에서 정해야 한다. 경계는
조회할 수 있어도 전체 면을 기본 표시하지 않는다는 점을 구분한다.

## 연동·데이터 확인 사항

- 지도 라벨: 중심 좌표, 권역/구 급지, 순위·단계, 구의 권역 수, 충돌 우선순위에
  필요한 면적 정보가 필요하다.
- 단지 핀/상세: 실제 좌표와 권역 연결, 세대 수, 연식, 최근 거래 가격·대표 면적,
  null 표시·정렬 정책이 필요하다. 디자인 숫자는 데모이며 실제 값으로 사용하지 않는다.
- 검색: 공백 제거·대소문자 무시 부분 일치, 권역 5/구 3/단지 6개 제한과 정렬을
  서버 검색으로 처리할지 별도 검색 인덱스를 FE에 제공할지 계약해야 한다.
- 월드컵: 대진 ID·유형·후보 데이터, 사용자 식별, 투표/넘김 중복 처리와 실패 처리,
  집계 비율·공개 여부, 다음 대진, 누적 선택 수의 저장 범위가 필요하다.
- 타임라인: 익명 표시 이름·시간·선택 결과, 권역 필터, pagination/갱신 방식과
  목록을 숨기는 기준이 필요하다.
- 좌표: MD는 동쪽 약 180m·남쪽 약 310m 밀림을 기록하고 옛 측지계 가능성을
  제시한다. BE import는 `ST_SetSRID(..., 4326)`를 사용하며 좌표 변환은 확인되지
  않았다. SRID 지정은 좌표 변환이 아니므로 원본 CRS와 실제 지점으로 검증해야
  한다. FE에서 임의 오프셋을 적용하지 않는다. 한강을 뺀 권역 geometry도 확인한다.
- NAVER 기본 행정동·아파트 POI 숨김과 스타일 적용 가능 범위는 실제 SDK에서
  확인해야 한다. 이번 검토는 SDK 설정의 지원 여부를 검증하지 않았다.
- 폴더에는 MD가 참조하는 `house-screen.png`가 없었다. 집 그림·왕관·레일 로고·
  설명 그림과 아이콘은 Figma에서 확보하고 이미지 필터/합성 기준을 검증한다.

## 착수 순서

1. 기존 React·TypeScript·Vite 기반 프로젝트를 초기화한다.
2. Figma semantic tokens와 공통 컴포넌트를 구현하고 데스크톱·모바일 화면 틀을
   준비한다. 모바일 시안은 참고용이므로 세부 배치는 추가 확정한다.
3. MD 기준의 지도·권역 상세·검색 UI를 임시 fixture/MSW로 구현한다.
4. 기획 미정값은 명시적으로 분리하고, 확정된 월드컵 화면 동작을 mock으로 구현한다.
5. 새 화면 기준으로 BE 계약을 합의하고, 백엔드 생성 OpenAPI 사본을 받아 타입을
   생성한 뒤 실제 연동한다. mock 계약을 확정된 백엔드 OpenAPI로 취급하지 않는다.
6. 실제 지도 좌표·라벨 충돌·데이터량·좁은 화면 정책과 실패 상태를 검증한다.

화면 기준과 미정 항목은 [디자인 핸드오프 기준](../product/design-handoff.md)을 따른다.

## 사용자 확정 및 다음 작업 환경

2026-10-13 사용자가 모바일 웹도 지원하기로 확정했다. 모바일은 제품·QA 범위에
포함하며 기존 데스크톱 전용 정책을 대체한다. 모바일 시안 자체는 참고용이다.

브랜치를 개설하고 `--yolo` 옵션을 붙여 Orca workspace를 생성한다. 이 브랜치의 첫 작업은 프로젝트
초기화다. 이번 문서 기록·push 작업에는 브랜치/workspace 생성과 앱 초기화를
포함하지 않는다. workspace 생성 방법은 실제 Orca 환경에서 확인한다.

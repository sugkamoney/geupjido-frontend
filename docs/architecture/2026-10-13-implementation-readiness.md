# 백엔드·디자인 핸드오프 구현 준비 점검

> 확인 날짜: 2026-10-13 · 상태: UI/mock 개발 착수 가능, 실제 API 연동 대기

## 확인 범위와 한계

백엔드 원격 기본 브랜치 `develop`을 임시 폴더에 shallow clone하여 코드를
검토했다. 기준은 [`dfb7cc4282979232f616113dd25704ee0b38b405`](https://github.com/sugkamoney/geupjido-backend/tree/dfb7cc4282979232f616113dd25704ee0b38b405)
(2026-10-05, 실거래 수집 서비스 PR #71 병합)다. 원격 브랜치 이름도 조회했지만
모든 feature 브랜치의 코드를 검토한 것은 아니다. 서버를 실행하거나 실제 DB,
배포된 API, 백엔드 테스트를 검증하지 않았다. 백엔드 파일은 수정하지 않았다.

디자인 MD 00~09, 별도 기획 논의 문서, HTML 3개를 읽었다. Figma의 Foundations,
Components, Screens 구조와 메인 화면 변수, 메인·월드컵 선택 직후 스크린샷을
확인했다. 모든 화면·variant의 정밀 검증은 구현 시 진행한다. HTML은 브라우저
도구 연결 오류로 소스만 검토했으며 실제 클릭 동작을 테스트하지 않았다.

## 백엔드 구현 현황

| 영역 | 코드에서 확인한 구현 | FE 연동에 남은 일 |
|---|---|---|
| 지역·권역 | Region/City/Zone, repository, GeoJSON 경계 import, 공간 schema | 공개 지도 DTO·조회 API, 구 평균 급지·라벨 정보 |
| 단지 | Complex, repository, 목록·기본정보 수집, 단건·일괄 저장 runner | 좌표·권역 매핑과 활성화, viewport·상세·권역 내 순위 API |
| 실거래 | ApartmentTrade 모델·schema·repository, 외부 API client·mapper·collection service | 단지/권역 매핑, 저장·집계 흐름, 대표 가격·면적 갱신과 조회 계약 |
| 지도·검색 | 공개 controller 없음 | 경계·라벨·핀·검색 계약 정의 |
| 월드컵·투표·급지·사용자 | match/vote/tier/user는 package-info 수준 | 대진, 투표·넘김, 익명 식별/인증, 비율·타임라인·급지 산정 구현 |
| OpenAPI | Springdoc 의존성과 OpenApiConfig 존재 | 제품 endpoint 명세와 고정 JSON 산출물 |

`Complex` 생성 시 `zone`, `location`, `price`, `representativeArea`는 설정되지
않고 `active=false`로 시작한다. 필드가 존재한다는 사실만으로 화면에 쓸 실제
데이터가 준비되었다고 판단할 수 없다. 최신 실거래 collection service는 외부
응답을 모델 목록으로 변환해 반환하며, 해당 서비스 자체가 저장·가격 갱신을
수행하지 않는다.

## 기존 설계와 새 핸드오프의 차이

| 항목 | 9월 설계 | 새 디자인 동작 기준 |
|---|---|---|
| 지도 표시 | 시·권역 경계 Data Layer, 최신 원격 문서 기준 zoom 12~13 cluster / 14~21 complex | 구·권역 라벨, 선택한 권역만 면 표시, cluster UI 없음 |
| 줌 | 정수화해 API 요청 | 구/권역 12.5, 단지 핀 14.5, 최소 9.5·최대 17 |
| 권역 상세 | 구체 화면 미정 | 급지·단계·권역 내 단지 시세순 목록·비교 진입 |
| 제품 범위 | 지도 탐색 중심 | 검색·월드컵 모달·타임라인·내 선택 누적 판 포함 |
| 작은 화면 | 최소 QA 1280×720 | 시각 기준 1920×1080, 더 좁은 화면의 축소 정책 미정 |

기존 [지도 API 설계](../superpowers/specs/2026-09-19-map-api-and-runtime-design.md)의
cluster·zoom 규칙을 새 UI에 그대로 적용하지 않는다. SDK 실수 zoom과 서버 조회
zoom의 관계, viewport 상한·응답 제한 시 UX를 새 계약에서 정해야 한다. 경계는
조회할 수 있어도 전체 면을 기본 표시하지 않는다는 점을 구분한다.

## 연동·데이터 확인 사항

- 지도 라벨: 중심 좌표, 권역/구 급지, 순위·단계, 구의 권역 수, 충돌 우선순위에
  필요한 면적 정보가 필요하다.
- 단지 핀/상세: 실제 좌표와 권역 연결, 세대 수, 연식, 최근 거래 가격·대표 면적,
  null 표시·정렬 정책이 필요하다. 디자인 숫자는 데모이며 실제 값으로 사용하지 않는다.
- 검색: 공백 제거·대소문자 무시 부분 일치, 권역 5/구 3/단지 6개 제한과 정렬을
  서버 검색으로 처리할지 별도 검색 인덱스를 FE에 제공할지 계약해야 한다.
- 월드컵: 대진 ID·유형·후보 데이터, 사용자 식별, 투표/넘김 중복 처리와 실패 처리,
  집계 비율·공개 여부, 다음 대진, 누적 선택 수의 저장 범위가 필요하다.
- 타임라인: 익명 표시 이름·시간·선택 결과, 권역 필터, pagination/갱신 방식과
  목록을 숨기는 기준이 필요하다.
- 좌표: MD는 동쪽 약 180m·남쪽 약 310m 밀림을 기록하고 옛 측지계 가능성을
  제시한다. BE import는 `ST_SetSRID(..., 4326)`를 사용하며 좌표 변환은 확인되지
  않았다. SRID 지정은 좌표 변환이 아니므로 원본 CRS와 실제 지점으로 검증해야
  한다. FE에서 임의 오프셋을 적용하지 않는다. 한강을 뺀 권역 geometry도 확인한다.
- NAVER 기본 행정동·아파트 POI 숨김과 스타일 적용 가능 범위는 실제 SDK에서
  확인해야 한다. 이번 검토는 SDK 설정의 지원 여부를 검증하지 않았다.
- 폴더에는 MD가 참조하는 `house-screen.png`가 없었다. 집 그림·왕관·레일 로고·
  설명 그림과 아이콘은 Figma에서 확보하고 이미지 필터/합성 기준을 검증한다.

## 착수 순서

1. 기존 React·TypeScript·Vite 기반 프로젝트를 초기화한다.
2. Figma semantic tokens와 공통 컴포넌트를 구현하고 데스크톱·모바일 화면 틀을
   준비한다. 모바일 시안은 참고용이므로 세부 배치는 추가 확정한다.
3. MD 기준의 지도·권역 상세·검색 UI를 임시 fixture/MSW로 구현한다.
4. 기획 미정값은 명시적으로 분리하고, 확정된 월드컵 화면 동작을 mock으로 구현한다.
5. 새 화면 기준으로 BE 계약을 합의하고, 백엔드 생성 OpenAPI 사본을 받아 타입을
   생성한 뒤 실제 연동한다. mock 계약을 확정된 백엔드 OpenAPI로 취급하지 않는다.
6. 실제 지도 좌표·라벨 충돌·데이터량·좁은 화면 정책과 실패 상태를 검증한다.

화면 기준과 미정 항목은 [디자인 핸드오프 기준](../product/design-handoff.md)을 따른다.

## 사용자 확정 및 다음 작업 환경

2026-10-13 사용자가 모바일 웹도 지원하기로 확정했다. 모바일은 제품·QA 범위에
포함하며 기존 데스크톱 전용 정책을 대체한다. 모바일 시안 자체는 참고용이다.

다음 구현 작업을 시작할 때 최신 `main`을 기준으로 `feature/initialize-project`
브랜치를 개설하고 `--yolo` 옵션을 붙여 Orca workspace를 생성한다. 이 브랜치의 첫 작업은 프로젝트
초기화다. 이번 문서 기록·push 작업에는 브랜치/workspace 생성과 앱 초기화를
포함하지 않는다. workspace 생성 방법은 실제 Orca 환경에서 확인한다.

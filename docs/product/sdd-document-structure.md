# SDD 제품 문서 구조

> 상태: **확정** · 현재 버전: v0.2 · 최종 변경: 2026-09-20

## 목적

제품 요구사항을 기능별로 관리하고, 각 문서의 현재 기준과 변경 이력을 함께
보존한다. Notion의 기획 초안과 회의 기록을 구현 가능한 Git 기반 제품 기준으로
전환하는 것이 이 구조의 목적이다.

이 구조의 필수 구성과 운영 규칙은 `AGENTS.md`에도 기록한다. SDD 작업자는
기능 문서를 만들거나 갱신할 때 이 문서와 프로젝트 지침을 함께 따른다.

기술 구현 설계는 이 구조의 범위가 아니다. API 계약, 컴포넌트 경계, 상태와
데이터 흐름, 테스트 전략은 계속 `docs/architecture/`가 소유한다.

## 디렉터리 구조

```text
docs/product/
├── INDEX.md
├── platform-support.md
├── sdd-document-structure.md
└── specs/
    ├── INDEX.md
    ├── _templates/
    │   ├── README.template.md
    │   ├── requirements.template.md
    │   ├── acceptance-criteria.template.md
    │   └── decisions.template.md
    └── <feature-slug>/
        ├── README.md
        ├── requirements.md
        ├── acceptance-criteria.md
        └── decisions.md
```

`specs/`와 그 하위 폴더는 실제 SDD 작업을 시작하는 시점에 생성한다. 빈 기능
폴더를 미리 만들지 않는다. 급지도의 최초 대상 기능은 `map-exploration/`이다.

## 기능 문서의 책임

| 문서 | 현재 기준으로 기록할 내용 |
| --- | --- |
| `README.md` | 기능 목표, 대상 사용자, 범위, 문서 상태, 관련 Notion·아키텍처 문서 |
| `requirements.md` | 사용자 흐름, 화면 동작, 제품 정책, 데스크톱·모바일 웹 지원 범위 |
| `acceptance-criteria.md` | 구현 완료 여부를 판정하는 검증 가능한 사용자 시나리오 |
| `decisions.md` | 해당 기능에서 확정하거나 논의 중인 제품 결정과 다음 검토 시점 |

Notion은 기획 초안, 회의와 작업 보드의 협업 공간으로 유지한다. Git의 기능
문서는 현재 구현과 검증의 기준이며, 각 `README.md`에서 관련 Notion 페이지를
연결한다.

## 기술 문서와의 경계

제품 문서는 “사용자에게 무엇을 어떻게 제공하는가”를 기술한다. 다음 내용은
`docs/architecture/`에 한 번만 기록하고 제품 문서에서는 링크로 연결한다.

- API 요청·응답 계약과 인증 방식
- URL·클라이언트 상태·서버 상태의 소유 관계
- 컴포넌트와 모듈 경계
- 지도 SDK, 데이터 적재, 오류 처리와 성능 전략
- 자동화·수동 테스트의 구현 방법

예를 들어 지도 확대 단계의 사용자 표시 규칙은
`map-exploration/requirements.md`에, 확대 수준을 URL 상태와 지도 SDK에
동기화하는 방법은 `docs/architecture/`에 둔다.

## 버전과 변경 이력

각 기능 문서는 상단에 상태, 현재 버전, 최종 변경일을 표시한다.

```md
> 상태: 확정
> 현재 버전: v0.2
> 최종 변경: YYYY-MM-DD
> 관련 Notion: [문서 제목](URL)
```

본문은 항상 최신의 유효한 기준만 유지한다. 각 문서 마지막에는 다음 형식의
`변경 이력` 표를 둔다.

```md
## 변경 이력

| 버전 | 날짜 | 상태 | 변경 요약 |
| --- | --- | --- | --- |
| v0.2 | YYYY-MM-DD | 확정 | 변경한 정책 또는 검증 기준 |
| v0.1 | YYYY-MM-DD | 제안 | 최초 문서화 |
```

버전은 해당 문서 단위로 증가한다. 요구사항 변경이 수용 기준에 영향을 주면 두
문서 각각의 버전과 이력을 갱신한다.

대규모 정책 전환이나 외부 검토 기준처럼 과거 전문 보존이 필요한 경우에만
`versions/v0.1.md`처럼 기능 폴더 안에 불변 스냅샷을 추가한다. 일반적인 변경은
본문 복제 없이 변경 이력으로 추적한다.

변경의 대안, 배경과 trade-off가 장기적으로 중요한 경우에는
`docs/history/`에 ADR을 만들고, 기능 문서의 변경 이력 행에서 이를 연결한다.
기능 문서에는 현재 규칙을, ADR에는 결정 당시의 이유를 둔다.

## 상태와 운영 흐름

문서 상태는 `제안`, `확정`, `대체됨`을 사용한다.

1. Notion의 기획 초안 또는 회의 결과를 기능의 `requirements.md`에 현재 제품
   기준으로 정리한다.
2. 완료 판정에 필요한 시나리오를 `acceptance-criteria.md`에 기록한다.
3. 제품 정책의 미결·확정 사항은 `decisions.md`에서 관리한다.
4. 구현 설계가 필요하면 `docs/architecture/` 문서를 작성하고 두 문서를 서로
   연결한다.
5. 정책 또는 구현 완료 기준이 바뀌면 영향을 받은 각 제품 문서의 버전과 변경
   이력을 갱신한다.
6. 기능 기준이 대체되면 상태를 `대체됨`으로 바꾸고 대체 문서 또는 기능을
   연결한다.
